02: Google Cloudカードから内部ケーススタディ詳細へ接続 設計書

Goal Design Files Implementation Verification

Goal

  • Outcome: HomeのGoogle Cloud注目カードをクリックするとbegonia内のケーススタディ詳細へ移動し、構成図、想定シナリオ、設計判断、コスト、セキュリティと運用、本番化との差分を読める。GitHubは詳細ページから実装と出典を確認する副導線になる。
  • Reason: 現在の外部GitHubリンクだけでは、.design/first-mock/portfolio_prototype.htmlが示す「カードからポートフォリオ内で設計内容を読む」体験を満たさないため。
  • Scope: google-cloud-learning/architectures/01を出典とするGoogle Cloud注目カード1件、静的な内部詳細ルート、begonia向けに編集したケーススタディ本文、ローカル保持する構成図、出典コミットへのGitHubリンクを対象にする。
  • Out of scope: Azure・比較カードの詳細、Architecture Catalog、クラウド比較ページ、learningリポジトリの変更、GitHub APIや外部HTMLを使う自動同期、summary.htmlの埋め込み、CMS、実行時の外部通信。

Design

採用判断

採用: ローカルの編集済みスナップショットから静的な詳細ページを生成する

カードの主導線は同一タブの内部ページとし、GitHubを直接開かない。ケーススタディ本文と構成図は同じ出典コミットからbegoniaへ取り込み、ポートフォリオの読者向けに再構成する。Astroのビルド中や閲覧時にはGitHubへ取得に行かない。

README.mdはケーススタディの意味上の原本、architecture.svgは構成図の原本とする。summary.htmlは同じ情報から作られた独立した閲覧物であり、CSSやJavaScriptを含む任意HTMLをbegoniaへ持ち込まないため、取込元にはしない。

導入前から02で導入する状態への変更

導入前の基準（02で置き換える状態）

src/data/architectures.tsのArchitectureSummary.sourceとgetArchitectureSourceUrl()がGoogle Cloud 01のmainディレクトリURLを所有する。ArchitectureCard.astroはカード自体を<article>として描画し、その末尾に「Google Cloudの実装を見る」という外部リンクを置く。

src/pages/にはHomeだけがあり、Content Collection、ケーススタディ本文、構成図アセット、詳細ルートはない。astro.config.mjsにadapterやoutput指定はなく、現在のサイトはAstro既定の静的出力である。

02で導入する状態

Google Cloudカード全体を/architectures/google-cloud/01/への内部リンクにし、カード内のGitHub外部リンクを取り除く。詳細はローカルのContent Collectionから静的生成し、ページ末尾で取り込み元の固定コミットへリンクする。Azure・比較カードは詳細未接続の<article>を維持する。

カードの単位と増え方

この設計でいう1件の単位は、learningリポジトリのarchitectures/{architectureId}に対応する1アーキテクチャ・ケーススタディである。1件につきカード1枚、詳細エントリ1件、詳細URL 1本を持つ。同じ分類に属する複数アーキテクチャを1枚のカードへまとめない。

概念役割と多重度
アーキテクチャカードと詳細ページの所有単位。{provider, architectureId}の組を一意とし、1アーキテクチャ = 1カード = 1詳細エントリとする。
themes現在のコードでWeb / API、コンテナ、ネットワークなどを表す分類タグ。カードの所有単位ではなく、1カードが複数タグを持て、同じタグを複数カードが共有できる。画面と設計上は「分類タグ」と呼ぶ。
featuredHomeへ掲載するかを決める表示属性。アーキテクチャの存在や詳細ページの有無を表さない。件数が増えてもHomeはfeatured: trueのカードだけを表示する。

内部詳細IDは{公開用provider名}/{architectureId}とする。gcpの公開用provider名はgoogle-cloud、azureはazureである。タイトルや採用サービスが後から変わってもURLを変えず、クラウド間の同じ番号も衝突させないためである。たとえばGoogle Cloud 01・02はそれぞれ/architectures/google-cloud/01/、/architectures/google-cloud/02/となり、同じ「Web / API」分類でも別カード・別ページになる。Azure 02は/architectures/azure/02/となる。

カードとルート

  • ArchitectureSummaryは任意のdetailIdを持つ。Google Cloudカードにはgoogle-cloud/01を設定し、出典情報は詳細コンテンツへ移す。既存のカードidは表示データの識別子として維持し、URLには使わない。
  • detailIdがあるカードは、カード全体を単一の<a>で包み、同一タブの/architectures/{detailId}/へ遷移する。カード末尾にはリンク内の非対話要素として「ケーススタディを読む →」を表示する。
  • カード内に別のリンクやクリックハンドラーを置かない。リンクのアクセシブルネームはカードタイトルとし、ホバーだけでなく:focus-visibleでもカード全体の選択状態を示す。
  • detailIdがないAzure・比較カードはリンク、CTA、ポインターカーソルを持たない。これは02以前からある未接続モックの移行状態だけに許し、今後新しい実在アーキテクチャのカードを追加するときは同じ変更で詳細エントリも追加する。
  • src/pages/architectures/[...id].astroはgetStaticPaths()で詳細エントリだけを列挙する。未登録IDのHTMLは生成せず、クライアント側ルーターやJavaScriptは追加しない。

詳細コンテンツ契約

src/content.config.tsにarchitectureDetailsを定義し、src/content/architectures/**/*.mdをglob()で読む。エントリIDはsrc/content/architectures/からの相対パスとし、ArchitectureSummary.detailIdとの結合キーにする。Google Cloud 01はsrc/content/architectures/google-cloud/01.mdが所有する。

所有先・フィールド契約
ArchitectureSummary.detailId?対応するarchitectureDetailsのエントリID。省略は既存の未接続モックに限り、出典のある新規アーキテクチャカードでは必須とする。
description詳細ページの導入文とmeta descriptionに使う、空でない文字列。カードのタイトルやサービス一覧は重複保持しない。
sourceprovider: 'gcp' | 'azure'、owner: 'MasanaoAsato'、providerに対応するrepository、空でないarchitectureId、40桁の小文字16進数revisionを持つ。gcpはgoogle-cloud-learning、azureはazure-learningだけを許可する。revisionは取り込んだREADMEとSVGが存在するmainのコミットとする。
diagram / diagramAltdiagramは同じディレクトリのローカル画像をAstroのimage()で検証する。diagramAltは図から読み取れる公開経路を説明する空でない日本語文字列とする。
Markdown本文ページのh1はテンプレートが所有するため、本文はh2から始める。必須見出しは「想定シナリオ」「設計判断」「コスト試算」「セキュリティと運用」「学習スコープと本番化への差分」とし、この順に各1件置く。

getStaticPaths()は、各詳細エントリを参照するArchitectureSummary.detailIdが1件だけあり、entry IDがsource.providerから得る公開用provider名とsource.architectureIdの組に一致することを検証する。逆に、すべてのdetailIdにも詳細エントリが必要である。さらにrender(entry).headingsの深さ2の見出しを上記の必須見出しと順序まで照合する。いずれかが不一致なら、重複カード、リンク切れ、不完全なケーススタディを公開しないようビルドを失敗させる。

出典の取得と編集

公開済みのmainから取込対象の1コミットを固定し、次の対応で取り込む。取得と編集はbegoniaの変更としてレビューし、自動同期は行わない。

出典begoniaでの扱い
architectures/01/README.mdの導入・想定シナリオdescriptionと「想定シナリオ」へ要約する。公開対象、独自ドメイン、LB経由限定、学習用の一時構成という前提を落とさない。
READMEのADR-001〜ADR-003各ADRの背景、決定、比較、影響を「設計判断」に残す。Terraformコードから新しい理由を推測して追加しない。
READMEのコスト試算計算基準日、3時間、リクエスト数、通信量、除外費用、常設時の比較を一体で保持する。金額だけを切り出さない。
READMEのセキュリティ、確認と削除、テーマの範囲、学び実装済みの制御と対象外の認証・高可用性・継続監視を区別し、「セキュリティと運用」「学習スコープと本番化への差分」へ再構成する。
architectures/01/architecture.svgREADMEと同じコミットのファイルをsrc/content/architectures/google-cloud/01.svgへ保存する。外部URLで表示せず、インライン展開もしない。
architectures/01/summary.htmlとTerraform一式本文として取り込まない。Terraformは詳細ページ末尾のGitHub出典リンクから参照させる。

出典更新を反映するときは、README、SVG、編集済みMarkdown、source.revisionを同じbegonia変更で更新する。本文だけ、または図だけを別コミット由来にしない。

詳細ページ表示

  • BaseLayout.astroを使い、meta titleは「{カードタイトル} | Cloud Architecture Lab」、meta descriptionはエントリのdescriptionとする。
  • 冒頭はHomeへ戻るパンくず、Google Cloudと分類タグのバッジ、カードと同じh1、導入文を表示する。未実装のCatalogへのリンクは置かない。
  • 構成図はローカルアセットを通常の画像として表示し、diagramAltを代替テキストに使う。SVGをページDOMへインライン展開しない。
  • 構成図の後にMarkdown本文を描画する。数値を含むコストは表、各ADRはh3以下のまとまりとして、狭い画面でも横スクロールまたは折返しで欠落なく読めるようにする。
  • 末尾に「GitHubで実装と出典を見る ↗」を置き、source.revisionを使うhttps://github.com/{owner}/{repository}/tree/{revision}/architectures/{architectureId}へリンクする。新しいタブで開き、rel="noopener noreferrer"を付ける。

失敗時と互換性

  • Content Collectionのschema違反、画像欠落、summaryとdetailの結合不一致、必須h2欠落はビルドエラーにする。
  • GitHubの障害や削除は既に生成された詳細ページと構成図の表示へ影響させない。外部リンク到達性はビルド条件にせず、固定コミットがGitHubから消えた場合は次のbegonia変更で出典を修正する。
  • FeaturedArchitecturesからArchitectureCardへ渡すProps境界は維持し、呼び出し側でURLを組み立てない。
  • 既存のid、カードタイトル、サービス、バッジ、Homeのカード配置は維持する。内部識別子gcpも改名しない。

Implementation

  1. 出典を確定: 公開済みのgoogle-cloud-learning/mainから、Google Cloud 01のREADMEとSVGを含むコミットの完全SHAを確定する。
  2. ローカルコンテンツを作成: 同じSHAからREADMEとSVGを取得し、schemaに従うMarkdownへ編集してbegoniaへ保存する。
  3. 静的詳細を接続: Content Collection、結合検証、動的ルート、詳細表示を追加してから、カードの外部リンクを内部リンクへ置き換える。これにより、カードが先に未生成ページを指す中間状態を作らない。
