ケーススタディ（アーキテクチャ）追加手順

この手順だけで、AzureまたはGoogle Cloudの実在アーキテクチャを、サイトの一覧と静的詳細ページへ追加できます。通常の追加ではアプリケーションコードを変更しません。

完了条件変更前のルール追加手順原稿テンプレート検証失敗時の対処

完了条件

  1. Homeに新しいカードが指定順で表示され、/architectures/{provider}/{architectureId}/へ遷移できる。
  2. 詳細ページに構成図、5つの本文セクション、出典GitHubのmain/architectures/{architectureId}へのリンクが表示される。
  3. pnpm run build、pnpm run check、git diff --checkがすべて成功する。

変更前のルール

追加の単位

1アーキテクチャは、Markdown原稿1件と構成図SVG 1件です。カードのタイトル、クラウド、分類、サービス、掲載順、本文、出典はすべてMarkdownのfrontmatterと本文から作られます。

cloud原典リポジトリMarkdownの置き場所詳細URL（ブラウザ）図の置き場所（リポジトリ内）
azureMasanaoAsato/azure-learningsrc/content/architectures/azure/{architectureId}.md/architectures/azure/{architectureId}/public/architectures/azure/{architectureId}.svg
gcpMasanaoAsato/google-cloud-learningsrc/content/architectures/google-cloud/{architectureId}.md/architectures/google-cloud/{architectureId}/public/architectures/google-cloud/{architectureId}.svg
  • architectureIdは原典のarchitectures/{architectureId}のディレクトリ名と完全一致させます。02を2へ変換しません。
  • 使えるthemesはweb、container、network、dataだけです。
  • sortOrderは全記事で重複しない0以上の整数です。Homeでは小さい順に並びます。
  • featured: trueならHomeへ表示されます。falseでも詳細ページは生成されますが、Homeには載りません。
この手順の対象外

新しいクラウド、未登録の分類、原典リポジトリ名の変更、または本文の5セクション構成を変える場合は、この手順だけでは追加できません。src/content.config.tsとsrc/utils/architectures.tsの契約を変更する設計・実装作業として扱ってください。

追加手順

最終的に必要なファイルと設定先

通常の追加では、下表の新規2ファイルだけを作成します。Homeの注目枠を切り替えるときだけ、既存Markdown 1件も編集します。

1

追加計画を決める

作業を始める前に、下表を埋めます。以後のパスとfrontmatterはこの値をそのまま使います。例はAzureの02です。

項目Azure 02の例決め方
cloudazureAzureならazure、Google Cloudならgcp。
architectureId02原典のarchitectures/02と同じ文字列。
entry IDazure/02Azureはazure/{architectureId}、GCPはgoogle-cloud/{architectureId}。
sortOrder30既存値と重複しない値。現在の最大値より10大きい値を使う。
featuredtrueHomeに載せるならtrue。
cd /home/ubuntu/workspace/begonia
rg -n "^(sortOrder|spotlight):" src/content/architectures
git status --short

既存の変更が表示された場合も、その変更を上書きせず、新記事に関係するファイルだけを編集します。

2

原典を確定し、revisionを記録する

原典リポジトリのarchitectures/{architectureId}に、少なくともTerraform等の実装、README.md、architecture.svgがある状態にします。原典がローカルにない場合は先にcloneし、内容を確定させます。

# Azureの例。GCPでは azure-learning を google-cloud-learning に置き換える。
git clone https://github.com/MasanaoAsato/azure-learning.git /tmp/azure-learning
git -C /tmp/azure-learning switch main
git -C /tmp/azure-learning pull --ff-only
git -C /tmp/azure-learning rev-parse HEAD
git -C /tmp/azure-learning status --short
test -f /tmp/azure-learning/architectures/02/README.md
test -f /tmp/azure-learning/architectures/02/architecture.svg

git status --shortは何も表示しないことを確認します。表示がある原典はスナップショットとして使わず、必要な変更をコミットしてから、または意図的に不要な変更を取り除いてから、この手順をやり直します。rev-parse HEADの40桁の小文字SHAを後のsource.revisionへそのまま記録します。これはポートフォリオへ取り込んだ原典のスナップショットです。一方、詳細ページの「GitHubで最新の実装を見る」は原典リポジトリのmainを開きます。

3

構成図を静的アセットとして追加する

原典の図を変更せずにコピーします。SVGはMarkdownと同じsrc/contentには置かず、必ずpublicに置きます。

# Azure 02の例
mkdir -p public/architectures/azure
cp /tmp/azure-learning/architectures/02/architecture.svg public/architectures/azure/02.svg
test -s public/architectures/azure/02.svg

# Google Cloud 02の場合
# mkdir -p public/architectures/google-cloud
# cp /tmp/google-cloud-learning/architectures/02/architecture.svg public/architectures/google-cloud/02.svg
# test -s public/architectures/google-cloud/02.svg

この結果、Azure 02のdiagram値は/architectures/azure/02.svgになります。ファイル名、URL、frontmatterの値は完全一致させます。

4

Markdown原稿を作成する

次のテンプレートを、Azureならsrc/content/architectures/azure/{architectureId}.md、Google Cloudならsrc/content/architectures/google-cloud/{architectureId}.mdに保存します。[[...]]を残さず、すべて実際の値に置換します。タイトルや説明に:、#、先頭の[などYAMLとして解釈される文字を含めるときは、値全体をダブルクォートで囲みます。

5

本文を原典から再構成する

  • 想定シナリオ: 利用者、解決する課題、到達経路、対象外の要件を示します。
  • 設計判断: ADRごとに背景、決定、比較した選択肢、影響を記述します。Terraform等の実装で確認できる事実だけを「実装済み」とします。
  • コスト試算: 料金確認日、リージョン、稼働時間、SKU、利用量、合計、含まない費用を明記します。
  • セキュリティと運用: 実装済みの制御、検証方法、学習後の削除手順を記述します。秘密情報は掲載しません。
  • 学習スコープと本番化への差分: この題材で扱う範囲と、本番化で別途設計する項目を分けます。
見出しの制約

本文のh2はテンプレートの5つだけで、順序も完全一致が必要です。構成図はページが自動表示するため## 構成図を追加しません。小見出しは###以下を使います。

6

Homeへの掲載と注目枠を確認する

通常は新記事のMarkdownにfeatured: trueを設定し、Homeの一覧へ載せます。spotlightは、Home上部の「注目のケーススタディ」に表示する1記事だけを指定するfrontmatterです。

  1. 注目記事を変えない場合: 新記事にはspotlightを設定しない。既存の注目記事はそのまま残す。
  2. 新記事を注目記事にする場合: 現在の注目記事Markdownからspotlight:ブロック全体を削除し、新記事MarkdownのsortOrderの直後へ次のブロックを追加する。
新記事のMarkdownに追加するspotlightブロック

labelは注目枠の見出し、descriptionは補足文です。記事の構成図、タイトル、説明、サービス、詳細リンク、出典リンクは、同じMarkdownのほかのfrontmatterから自動で表示されます。

spotlight:
  label: 注目のケーススタディ
  description: 構成図・要件・判断・実装を、ひとつの実例として読めます。

Azure 02を例にしています。Google Cloudの場合は、cloudをgcp、providerをgcp、repositoryをgoogle-cloud-learning、パスをgoogle-cloudに置換します。

検証と完了確認

7

自動検証を実行する

pnpm run build
pnpm run check
git diff --check

pnpm run buildはfrontmatterの型、クラウドと原典の対応、entry ID、sortOrderの重複、spotlightの件数、5つのh2の順序、静的ルート生成を確認します。

8

ブラウザで確認する

pnpm exec astro dev --background
pnpm exec astro dev status

表示されたURL（通常はhttp://localhost:4321/）でHomeを開き、次を確認します。

  • 新カードがsortOrderの昇順で表示される。
  • カードのクラウド名、分類、タイトル、利用サービスがfrontmatterどおりである。
  • カードを開くと、Azureは/architectures/azure/{architectureId}/、GCPは/architectures/google-cloud/{architectureId}/になる。
  • 構成図が表示され、5つのセクション、出典リンク、クラウドに対応するアクセント色が表示される。
pnpm exec astro dev stop

確認後は必ず開発サーバーを停止します。

9

変更範囲を最終確認する

git status --short
git diff -- src/content/architectures public/architectures

通常の追加で変更されるのは、新しいMarkdownとSVGだけです。注目枠を移した場合だけ、既存Markdown 1件のspotlightも変更されます。それ以外のソースコード変更がある場合は、意図を確認してから進めます。

失敗時の対処

表示されたエラー・症状確認・修正すること
sortOrder は重複できませんrg -n "^sortOrder:" src/content/architecturesで既存値を確認し、新記事の値を未使用の整数へ変える。
spotlight は1件だけ設定してください全Markdownのspotlight:を確認する。0件なら既存または新記事の1件に追加し、2件以上なら残す1件以外を削除する。
cloud と source.providerまたはsource.repositoryが一致しないAzureはazure / azure-learning、GCPはgcp / google-cloud-learningにそろえる。
詳細IDと source.architectureId が一致しませんMarkdownのパス、architectureId、diagramの番号を確認する。GCPのパスだけはgoogle-cloud/{architectureId}である。
必須見出しの順序が不正です本文の##をテンプレートの5つだけにし、文字列と順番を一致させる。小見出しは###へ下げる。
ビルドは成功するが図が表示されないdiagramが/architectures/...で始まるか、対応するpublic/architectures/...のSVGが存在し空でないかを確認する。ファイル名の大文字・小文字も一致させる。
Homeに出ないfeatured: trueにし、frontmatterが閉じる---の内側にあることを確認する。
