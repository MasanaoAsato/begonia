ブログ記事追加手順

この手順だけで、Content CollectionへMarkdown記事を追加し、ホームのブログ一覧と静的記事ページで公開できます。

記事の契約 追加手順 確認 トラブルシューティング

記事の契約

通常の記事追加で変更するファイルは、src/content/blog/配下のMarkdownだけです。Content Collection、ホーム一覧、カード、記事ルートは実装済みなので、src/content.config.tsやAstroコンポーネントを記事ごとに編集しません。

ファイルパス・ID・URL

MarkdownファイルCollection ID記事URL
src/content/blog/architecture-decisions.md architecture-decisions /blog/architecture-decisions/
src/content/blog/azure/cost-basics.md azure/cost-basics /blog/azure/cost-basics/

拡張子を除いたsrc/content/blog/からの相対パスがIDになります。公開後はURLを維持するため、ファイルの改名・移動をしません。新しいファイル名は小文字とハイフンの組み合わせを推奨します。

frontmatterフィールド

フィールド必須値使われる場所
title必須空でない文字列記事ページの唯一のh1、カード見出し、ページタイトル
description必須空でない文字列カードの要約、記事ページの導入文、meta description
publishedAt必須日付として解釈できる値。YYYY-MM-DDで記述公開日表示、並び順。新しい記事が先
tags必須空でない文字列を1件以上持つ配列カードと記事ページのタグ
draft任意boolean。未指定はfalse下書き制御。productionでは一覧・記事ページから除外

上記以外のslug、author、cover、urlなどのfrontmatterは、このサイトの記事契約にはありません。追加のメタデータが必要な場合は、記事追加手順の範囲を超えるスキーマ設計として扱います。

見出しの規則: ページのh1はfrontmatterのtitleから自動生成されます。本文で# 見出しを使わず、本文の最初の見出しは##から始めてください。

追加手順

1. リポジトリと依存関係を準備する

  1. リポジトリのルートへ移動します。 
    cd /home/ubuntu/workspace/begonia
  2. Node.jsは>=22.12.0を使います。依存関係が未インストールなら、リポジトリの通常のセットアップ手順に従ってnpm installを一度実行します。
  3. 作業ツリーに自分の作業以外の変更がある場合は、それを上書きしません。開始前に確認します。 
    git status --short

2. Markdownファイルを作成する

初回は記事ディレクトリを作成し、記事IDにしたいファイル名でMarkdownを作ります。以下ではarchitecture-decisionsを例にします。

mkdir -p src/content/blog
vi src/content/blog/architecture-decisions.md

エディタで次のfrontmatterを先頭に記述します。タイトルや説明に:、#、先頭の[などYAMLとして解釈される文字を含める場合は、値全体をダブルクォートで囲みます。

---
title: "設計判断を記録するためのブログ運用"
description: "アーキテクチャの判断と検証結果を、あとから再利用できる形で記録する方法を整理します。"
publishedAt: 2026-08-21
tags:
  - "Architecture"
  - "Astro"
draft: false
---

## 背景

この記事で扱う課題と、読者が得られる結果を書きます。

## 設計判断

採用した方法、採用理由、トレードオフを記録します。

## 検証結果

実行した確認と、残っている制約を書きます。

上の本文は例です。実際の記事では、タイトルとdescriptionの約束を本文の内容と一致させ、本文の見出しは記事ごとのテーマに合わせて追加します。

3. 下書きとして確認する

執筆途中はdraft: trueにします。developmentでは下書きも一覧と記事ページに表示され、productionでは下書きがホームにも静的記事ルートにも出力されません。

公開するときはdraft: falseにするか、frontmatterからdraft行を削除します。値を文字列の"true"や"false"にしないでください。スキーマが要求するbooleanではありません。

4. 開発サーバーで表示を確認する

リポジトリの規約に従い、バックグラウンドで開発サーバーを起動します。

astro dev --background
astro dev status

astroコマンドがPATHにない場合は、同じ処理を次のnpmスクリプト経由で実行できます。

npm run astro -- dev --background

通常のポートは4321です。実際のポートはastro dev statusまたはastro dev logsで確認し、次の2つをブラウザで開きます。

  • ホーム: http://localhost:4321/ — 第3領域「ブログ記事一覧」にカードが表示される。
  • 記事: http://localhost:4321/blog/architecture-decisions/ — タグ、公開日、タイトル、description、Markdown本文が表示される。

下書きの確認が終わったら、公開記事として確認できるようdraft: falseへ戻します。

5. productionビルドで確認する

frontmatterの型、Markdownの読み込み、静的記事ルート、ホーム一覧への接続をまとめて確認します。

npm run check
npm run build

公開記事のIDを自分の値に置き換え、生成物が存在することを確認します。ネストしたIDの場合も、スラッシュをそのまま使います。

ARTICLE_ID=architecture-decisions
test -f "dist/blog/$ARTICLE_ID/index.html"
printf 'generated: %s\n' "dist/blog/$ARTICLE_ID/index.html"

productionビルドではdraft: trueの記事に対応するdist/blog/...が生成されません。これは意図した公開制御です。

6. 差分と完了条件を確認する

git status --short
git diff --check
完了条件:
  • 記事Markdownがsrc/content/blog/にあり、IDとURLが意図どおりである。
  • ホームの#blog-indexに公開記事カードが表示され、カードから記事URLへ移動できる。
  • 記事ページにfrontmatterと本文が表示され、本文の最初の見出しがh2である。
  • npm run checkとnpm run buildが成功する。
  • 自分の意図しないファイル変更が差分に含まれていない。

確認が終わったら、開発サーバーを停止します。

astro dev stop

トラブルシューティング

症状確認すること
blogPostsのスキーマエラー title、description、publishedAt、1件以上のtagsがあるか確認します。draftはbooleanで記述します。
ホームにカードが出ない productionではdraft: trueが除外されます。公開する記事はfalseまたは未指定にし、開発サーバーを再読み込みします。
記事URLが404になる ファイルパスから拡張子を除いたIDとURLを一致させます。ネストしたファイルは/blog/親ディレクトリ/ファイル名/です。
記事の日付順が想定と違う publishedAtは新しい日付が先です。同じ日付の場合はIDの昇順になります。表示はAsia/Tokyo基準です。
本文の見出し構造が崩れる frontmatterのtitleがページのh1です。本文の#を##以上へ変更します。
ビルド時に空コレクション警告が出る 記事がまだ1件もない場合の警告は、空状態を許容する設計によるものです。記事ファイルを追加した後に再実行し、生成された記事URLを確認します。
